# Decider QLoRA学習 検証記録(第1回)

**位置づけ**: これは一般的な学習方針や推奨手法を示すものではない。`datasets/for-decider-ja/` の合成データセット(この回に限って用意されたもの)で Decider(`Mapika/decider-4b`)を QLoRA 継続学習した場合に、jev-ja-lab の標準35データセット評価でどう動いたかを記録した検証ログである。再現する際はデータセット・学習設定・評価設定が変われば結果も変わる前提で読むこと。

## 背景・目的

ユーザーが `datasets/for-decider-ja/` に Decider 公式の学習データ方針に沿って作成した日本語 Jev タスク用合成データセットを用意し、Decider 公式の学習方針(GitHub `Mapika/decider`)に従って学習を行い、学習前後で jev-ja-lab の標準ベンチマークがどう変化するかを確認する、という依頼に基づく。

Decider 公式の「Train your own」は Qwen3.5-*-Base からの1エポック・フルパラメータ教師あり CE ファインチューン(`decider.train`、`scripts/train.sh`)が基本形だが、小規模継続学習ではチームの `decider-12b v2` と同様に LoRA を使っている前例がある(`docs/CHANGELOG.md`)。本検証ではこの「LoRA 継続学習」の形を採用し、かつ GPU 制約(後述)から 4bit 量子化(QLoRA)を組み合わせた。

## 学習データ

`datasets/for-decider-ja/` の2ファイル、計18,258件:

- `programmatic-all.parquet`(16,000件): 決定論的に解いて検証済みの算術・論理判定タスク(choice 12,800件 / bool 3,200件)。日本語の短い状況設定+数値計算または条件判定。
- `SeeDummy_jev_native_reasoning_2258rows.parquet`(2,258件): 実日本語コーパス文書(`Podtech/llm-jp-corpus-v4-ja_wiki` 等由来)を土台にした文書根拠型の決定タスク。choice 323件・noul 930件・score 1,005件。teacher distillation 用の確率分布・reasoning も同梱されているが、本学習では使っていない(後述)。

`scripts/build_decider_ja_corpus.py` で decider 本体の `decider.data.core.Example`/`Q` 形式(`context, [Q(text, options, gold)], task`)に変換し、タスクごとに5%を held-out eval に分離(train 17,346件 / eval 912件、5タスクバケツ)。`programmatic` は choice は `answer_index` を、bool は `answer_bool` から対応する選択肢の `index` を gold とした。`SeeDummy` は `target_index` をそのまま gold とした。teacher の reported distribution / reasoning は decider 公式 `decider.train` の損失関数(交差エントロピー、オプションで Brier)がハード gold index しか使わないため今回は未使用。

## 学習方法: QLoRA(4bit量子化+LoRA)

### なぜフルファインチューンではないか

Decider 公式スクリプトはフルパラメータ bf16 AdamW 学習(`python -m decider.train`)。`Mapika/decider-4b`(Qwen3.5-4B-Base、約4.3B params)をこの方式でやると、重み+勾配+Adam状態だけで概算32GB超が必要になる。本機のGPUは16GB(RTX 5070 Ti)1枚のみで、フルファインチューンは収まらない。

### 採用した方式

`scripts/train_decider_ja_qlora.py` を新規作成。decider 公式パッケージの `make_items`/`batches_by_tokens`/`loss_fn`(`decider.train`)とデータパイプライン(`decider.data`)、LR スケジュール(cosine)は一切変更せず再利用し、モデル構築部分とoptimizerのみ差し替えた:

- バックボーンを bitsandbytes で 4bit(NF4, double quant, bf16 compute)量子化してロード。
- `lm_head` は量子化・学習対象から除外して bf16 のまま凍結(decider の `slot_logits` は `lm_head.weight` の該当行を直接タスクヘッドとして読むため、量子化・ラップされたレイヤーだと壊れる)。
- LoRA アダプタを Attention + MLP の全射影層に付与: full_attention層の `self_attn.{q,k,v,o}_proj`、linear_attention層の `linear_attn.{in_proj_qkv,in_proj_z,in_proj_b,in_proj_a,out_proj}`、両層共通の `mlp.{gate,up,down}_proj`(Qwen3.5はこの2種の層が混在するハイブリッド構成)。
- 学習対象パラメータは LoRA 部分のみ(後述の r=64 設定で 129.9M / 4.34B = 2.995%)。

### 学習設定(ユーザー指定)

| 項目 | 値 |
|---|---|
| ベース | `Mapika/decider-4b` のタグ `main`(=このプロジェクトの呼称で `v2.1`。コミット `eb5fbdfc9448473ec25e399882912863afbdb70e` に固定) |
| LoRA rank | 64 |
| LoRA alpha | 128 |
| LoRA dropout | 0.05 |
| 対象層 | Attention + MLP 全射影(上記) |
| Epoch | 2 |
| 学習率 | 1e-4 |
| Warmup | 全step数の5%(実測9 step) |
| Scheduler | Cosine |
| Token/step(実効) | 65,536(micro-batch max_tokens=4096 × accum=16) |
| Seed | 0 |
| 学習件数 | train 17,346件(ユーザー想定の29,325件/1,518stepとは一致しない。実際のコーパス件数で計算し直した結果、2epochで178 stepになった) |
| 学習後 | LoRA を bf16 本体へ merge(`scripts/merge_decider_ja_qlora.py`、`PeftModel.merge_and_unload()`) → `models/decider-ja-qlora/` |
| RL | なし(教師ありCEのみ) |

### 学習中のトラブルと対処

1度目の試行(r=16, epoch=3, max_tokens=6144)で、最初の periodic eval 直後に GPU メモリが 11.8GB→15.5GB に張り付き、速度が 1040→178 tok/s まで低下(CUDAアロケータの断片化が原因と推定)。中間チェックポイントが無い設計だったため、ユーザー判断で一旦停止し、以下を追加した版(今回採用した設定)で再実行した:

- `run_eval` 側の バッチトークン上限を 24576→4096、バッチサイズを 32→8 に縮小。
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`(本機Windows環境では未対応の旨の警告が出るが、無害)。
- 15 step ごとにチェックポイント保存(adapter + optimizer state + RNG状態、ディレクトリは `results/train-decider-ja-qlora/checkpoint/` 1つのみを上書き、増殖させない)、再実行時は自動resume。

再実行(r=64構成)はメモリ 11.1GB で全178step完走、クラッシュなし。

### 学習内 held-out eval(参考、ベンチマークとは別)

5タスクバケツ(programmatic choice/bool, SeeDummy choice/noul/score)の held-out 912件に対する in-corpus 精度:

| step | 全体acc |
|---|---|
| 30 | 0.937 |
| 60 | 0.944 |
| 90 | 0.939 |
| 120 | 0.949 |
| 150 | 0.961 |
| 178(最終) | 0.961 |

これは学習データと同じ分布・同じタスク形式での精度であり、下記の外部ベンチマーク(汎化性能)とは別物。

## ベンチマーク方法

jev-ja-lab の標準35データセット評価(Noul 14 / Choice 9 / Score 12)を、同一ベースモデルの学習前後で比較した:

- **baseline**: `Mapika/decider-4b`(タグ `main`/コミット `eb5fbdfc9448473ec25e399882912863afbdb70e`)を zero-shot でそのまま評価。学習時に実際に使ったコミットと同一であることを優先し、既存README比較表の `decider-4b-v2`(別コミット)とは意図的に区別した。
  設定: `configs/eval/decider-ja-main-baseline-series.yaml` → `results/eval-decider-ja-main-baseline-series/`
- **QLoRA後**: 上記 merge 済みモデル(`models/decider-ja-qlora/`)を同じ35データセットで評価。
  設定: `configs/eval/decider-ja-qlora-series.yaml` → `results/eval-decider-ja-qlora-series/`

## 考察(今回のデータセット・設定に限定した所見)

- **Choiceの数値推論系が明確に伸びた**: gsm8k_ja_mc10(+0.126)、gsm8k_ja_mc4(+0.033)、jgpqa_diamond(+0.035)、mgsm_ja(+0.016)。学習データの過半を占める `programmatic-all`(決定論的に検証済みの算術・論理choice/bool)の効果が、形式の異なる数値推論系choiceにも波及したと見られる。
- **Scoreは総じて微減**: wrime_joy(-0.067)、helpsteer_complexity(-0.040)、synthetic系も軒並み微減。学習データのscore例は `SeeDummy` 内の1,005件のみ(かつheld-out分離後は評価に使った母数も50件程度)で、score primitiveへの訓練信号が薄く、既存の調整(temperatureなど)を崩した可能性がある。
- **Noulは個別には動くが相殺して全体はほぼ横ばい**: jad_afc系(クレーム真偽判定、+0.05台)とtextdetox(+0.072)は伸びる一方、jcola系(文法性判定、-0.05台)とjnli_contradiction・wrime系が沈み、合算でほぼ差が出なかった。
- **Overallは+0.003で誤差の範囲**。全体としては「悪化はしていないが明確な向上とも言えない」結果であり、primitive間で効果の出方が大きく偏っている点が特徴。

この結果は今回の学習データ構成(programmatic=choice/bool中心、SeeDummyは3primitiveに分かれるが総数が少ない)・ハイパーパラメータ・評価データセットに固有のものであり、一般的な「DeciderをQLoRAで継続学習すると良い/悪い」という結論を意味しない。primitiveごとの訓練データ比率を変える、score例を増やす、epoch/lr/rankを振るなどすれば結果は変わりうる。
